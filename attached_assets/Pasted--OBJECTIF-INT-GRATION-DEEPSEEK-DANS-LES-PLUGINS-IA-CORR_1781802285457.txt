#  TÂCHE 1 : INTÉGRATION DEEPSEEK DANS TOUS LES PLUGINS IA (CRITIQUE)

**Contexte** : DeepSeek est actuellement configurable dans `/admin/api-keys`, mais il n'est pas utilisable dans les modules IA (AI SDR, Deal Coach, Executive, Knowledge, Meetings).

## 1.1 Backend : Mise à jour du Service LLM Central
Modifie le service central de gestion des LLM (ex: `LLMService.ts` ou `AiService.ts`) :
- Ajoute DeepSeek dans le registre des providers supportés.
- Configure l'endpoint de base de DeepSeek (`https://api.deepseek.com/v1`) et ses modèles par défaut (`deepseek-chat`, `deepseek-coder`).
- Modifie la méthode de génération pour gérer DeepSeek. L'API de DeepSeek étant compatible OpenAI, adapte le payload de la requête `fetch` en conséquence.
- Assure-toi que la méthode récupère dynamiquement la clé API DeepSeek stockée en base de données (via le service `ProviderKeysService`) avant de faire l'appel.

## 1.2 Backend : Mise à jour des Routes des Plugins IA
Pour chaque route de génération IA (AI SDR, Deal Coach, Executive Assistant, etc.) :
- Modifie la validation du body de la requête pour accepter 'deepseek' comme valeur valide pour le champ `provider`.
- Assure-toi que le paramètre `provider` est bien transmis au Service LLM central.

## 1.3 Frontend : Ajout dans les sélecteurs de Provider
Pour CHAQUE page contenant un sélecteur de modèle IA (AI SDR, Deal Coach, Executive Command, Knowledge Base, Meeting Intelligence) :
- Ajoute DeepSeek dans le tableau/la liste des providers disponibles.
- Donne-lui un label clair ("DeepSeek") et une icône distinctive (ex: 🔮 ou une icône lucide-react appropriée).
- Vérifie que lorsque DeepSeek est sélectionné, l'ID 'deepseek' est bien envoyé dans le corps de la requête API.

# 🐛 TÂCHE 3 : CORRECTION DU RSS FEED 403 (LE MONDE / LES ECHOS)

**Preuve** : Le cron de signaux échoue sur `https://www.lesechos.fr/rss/rss_tech.xml` avec un statut 403.

**Instruction** :
- Ouvre le service ou le fichier Cron qui gère le scraping RSS (`SignalCron.ts` ou `RssService.ts`).
- Modifie la fonction de fetch des flux RSS.
- Ajoute un header `User-Agent` réaliste (ex: un User-Agent de navigateur Chrome standard) et un header `Accept` pour le XML/RSS dans la requête `fetch`.
- Ajoute une gestion d'erreur propre : si le flux retourne un 403 ou 404, log un warning et retourne un tableau vide au lieu de faire planter le cron pour ce tenant.

#  TÂCHE 4 : NETTOYAGE DES LOGS NOTIFICATIONS STREAM 401

**Preuve** : Le frontend appelle `/api/v1/notifications/stream` sans token, reçoit un 401, puis rappelle avec le token.

**Instruction** :
- Ouvre le hook ou le composant frontend qui gère la connexion SSE des notifications (ex: `useSignalNotifications.ts` ou `NotificationCenter.tsx`).
- Ajoute une condition de garde (guard clause) au début du `useEffect` ou de la fonction de connexion : si le `accessToken` (ou le token JWT) n'est pas encore défini ou est nul, la fonction doit retourner immédiatement (`return`) sans tenter d'appeler l'API.
- Cela évitera le premier appel 401 inutile dans les logs backend.
