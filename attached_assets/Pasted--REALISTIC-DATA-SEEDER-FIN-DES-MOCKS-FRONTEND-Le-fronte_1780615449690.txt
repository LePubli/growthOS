## PARTIE A : Le "Action Logger" (Backend)
Crée un middleware/service `artifacts/api-server/src/lib/ActionLogger.ts`.
À chaque requête POST/PUT/PATCH/DELETE réussie (200/201), ce logger doit écrire dans la console un format très clair :
`[ACTION SUCCESS] Route: /api/v1/deals/:id | Action: UPDATE_STAGE | User: admin@epok.fr | DB Impact: 1 row updated | Payload: { stage: 'Negotiation' }`

Intègre ce logger dans toutes les routes de modification (deals, prospects, signals, sequences, etc.).

Crée un script de test backend : `artifacts/api-server/src/scripts/verify-e2e.ts`.
Ce script va simuler les actions critiques d'un utilisateur et vérifier que la DB a bien été modifiée.

Le script doit exécuter ces scénarios et afficher un rapport vert/rouge dans la console :

1. **Scénario Prospect** :
   - Créer un prospect via API (POST /prospects).
   - Vérifier en DB qu'il existe bien.
   - Modifier son score. Vérifier en DB que le score a changé.
   - Supprimer le prospect. Vérifier qu'il n'est plus en DB.
   - [✅ PASS] ou [❌ FAIL]

2. **Scénario Deal/Pipeline** :
   - Créer un deal.
   - Changer son étape de 'Lead' à 'Qualifié'.
   - Vérifier en DB que l'étape et la date de modification ont été mises à jour.
   - [✅ PASS] ou [❌ FAIL]

3. **Scénario Signal** :
   - Créer un signal.
   - Le marquer comme 'lu'.
   - Vérifier en DB que le champ `is_read` est passé à true.
   - [✅ PASS] ou [❌ FAIL]

4. **Scénario Séquence Email** :
   - Créer une séquence.
   - L'activer (toggle).
   - Vérifier en DB que le statut est 'active'.
   - [✅ PASS] ou [❌ FAIL]

Le script doit utiliser l'URL de l'API locale (http://localhost:3001) et un token JWT admin valide (généré dynamiquement ou en variable d'env).
Ajoute la commande `"test:e2e": "tsx src/scripts/verify-e2e.ts"` dans le package.json.
